# agent 向け規則のレビュー

リポジトリの agent 向け規則を監査し，原則に反する箇所を 1 件ずつ，場所・欠陥・修正案の形で返す．
引数にパスがあればそのファイルだけ，無ければ下記の対象すべてを読む．
引数に `--fix` があれば，報告の後に修正を適用して commit する．無ければ報告だけで止まる．

## 対象

次の順にたどって集める．

1. root と各ディレクトリの `AGENTS.md`，`CLAUDE.md`．
2. それらがリンクまたはパスで参照する文書（規則，方針，雛形）．
3. それらが名指す検査（pre-commit hook，lint，検査 script）．
4. `README.md`．人間向けだが，規則と食い違うことがある．

読む前に `writing-for-agents` skill を読む．context pointer，情報階層，完了条件，leading word，否定，剪定の語彙で欠陥を名指す．

## 原則

監査はこの 11 に対して行う．各原則は，守りたいこと（理由）と，そのための規則と，見つけ方からなる．
判定は規則の字面でなく理由に照らして行う．規則の形は守っているが理由を満たさない箇所も，理由は満たしているが規則の形を外れる箇所（行動規範のように状態で書けないもの）も，理由を基準に判断する．

1. **状態で書く**
   - 理由: 手順だけが書かれていると，agent は手順を終えたことを完了と見なし，手順が本来達成すべきことを確かめない．道具が変わるたびに手順は古びるが，達成すべき状態は変わらない．状態として書けば，agent はそれを自分で検証でき，手段を自分で選べる．
   - 規則: 規則は，agent が停止するときに成り立っているべき状態として書く．自動で行われる手順（hook が検査を実行する，など）は文章に書かない．価値観や判断の基準のように状態で書けないものは，そのまま残してよい．
   - 見つけ方: 「〜する」「〜してから〜する」の連なり．hook や formatter が担う手順への言及．各手順について「終わったとき何が成り立つべきか」を問い，それを書けるなら状態に直す．
2. **実行される規則だけ置く**
   - 理由: 誰も実行しない規則は，他の規則まで「守らなくてよいもの」に見せる．agent が判定できない起点を持つ規則は，agent が自分の都合で解釈し，実質的に無視される．
   - 規則: 誰も実行しない規則（定期レビューなど）や，agent が判定できない起点（「セッションの終了前」）を置かない．人の行為を要求する規則は，その人が実際に行う少数の行為に限る．
   - 見つけ方: 主語が人（ユーザ，レビュアー）の文をすべて拾い，一覧にして，それぞれ実際に行われているかを問う．起点が「〜前に」「〜後に」の文は，その時点を agent が知れるかを問う．
3. **1 つの意味は 1 か所**
   - 理由: 同じ規則が 2 か所にあると，片方だけが更新されて食い違い，agent はどちらに従うかを自分で決めることになる．更新する人も，どこを直せばよいか分からなくなる．
   - 規則: 同じ規則が複数のファイルにあれば，1 か所に残して他は削除かリンクにする．
   - 見つけ方: 規則ごとに，同じ意味の文を全ファイルから grep する．
4. **使う場所に置く**
   - 理由: root の `AGENTS.md` は毎ターン context に載るので，そこにある文はすべて注意を薄める．一方で，場面に結びつく規則はその場面で読まれなければ効かない．無関係な話題が同居した文書は，どの作業で読むべきかが決まらない．
   - 規則: ディレクトリに結びつく規則はそのディレクトリの `AGENTS.md` や雛形に置く．root の `AGENTS.md` には，どの作業でも効く規則と参照先だけを置く．規則の管理方針や雛形は root に置かない．1 つの文書には 1 つの話題だけを置く．
   - 見つけ方: root の `AGENTS.md` の各文について「どの作業でも効くか」を問う．参照される各文書について「特定のディレクトリや場面の話か」「話題が 1 つか」を問う．
5. **定義する．不要な概念は消す**
   - 理由: 定義の無い語は，読む agent ごとに違う意味になる．概念が増えるほど，規則の間の整合を保つ手間が増え，矛盾が入り込む．名前を付けることと規則を付けることを混ぜると，名前のために規則が増える．
   - 規則: 状態や用語はすべて定義する．定義できない概念，使われない概念，同じ物の別名は消す．名前は日常語にし，固有名は必要なときだけ付ける．概念に名前を付けるかと，それに規則を付けるかは分けて判断する．
   - 見つけ方: 定義なしに使われている語を拾う．1 つの語が 2 つの意味で使われていないか，1 つの物に 2 つの名前が無いかを見る．
6. **自然な日本語**
   - 理由: 規則の文書は agent が繰り返し読む文章の手本になる．直訳や不自然な語は agent の書く文章に伝染し，語の意味の曖昧さも伝染する．
   - 規則: 英語の動詞の直訳（close を「閉じる」，carry を「運ぶ」）は英語のまま書くか日本語の動詞で言い換える．日常語で書く．
   - 見つけ方: 「閉じる」「運ぶ」「開く（open question）」「住む」「走る」など．
7. **構造化する**
   - 理由: 1 文に複数の規則が詰まっていると，欠けている定義や規則どうしの矛盾が見えない．見出し，箇条書き，表に分ければ，1 つの規則を 1 つの単位として読み，検査し，削除できる．
   - 規則: 見出し，箇条書き，表で，1 文 1 規則にする．定義は定義として，規則は規則として分ける．
   - 見つけ方: 複数の規則が詰まった段落．定義と規則が混ざった文．
8. **文脈に依存しない**
   - 理由: 規則を読む agent は，それを書いた会話も過去の事故も知らない．過去への言及は，知らない読者には意味が取れず，知っている読者には今の規則と過去の経緯を混同させる．
   - 規則: 前のリポジトリ，移行，過去の事故に触れない．新しく入る agent が，その文書だけで迷わない．
   - 見つけ方: 固有の過去の名前，「以前は」「移行」，事故の経緯．
9. **環境の事実はコードが正**
   - 理由: コードから読める事実を文書に写すと，コードが変わったときに文書だけが古くなり，agent は古い値を信じる．文書に書く価値があるのは，コードが持てない事実だけである．
   - 規則: 設定値，パス，版など，コードや設定ファイルから読めるものを文書に写さない．文書には，コードに書けない事実（権限，人の合意）だけを置く．
   - 見つけ方: 数値，パス，版番号を含む文について，出典がコードにあるかを問う．
10. **リンクと整形は道具に任せる**
   - 理由: 人が手で保つもの（整形，参照の正しさ）は，いずれ崩れる．道具に任せれば崩れが検査で見つかり，規則として書く必要も無くなる．
   - 規則: ファイルへの参照は Markdown のリンクにする（リンク検査が壊れを拾う）．整形は formatter に任せ，手で揃えない．
   - 見つけ方: バッククォートで書かれたファイルパス．formatter の有無．

11. **理由を書く**
    - 理由: 理由の無い規則は，字面が当てはまらない場面で agent に判断の根拠を与えない．理由があれば，agent は規則の外の場面でも理由に沿って判断でき，理由が消えたときには規則を消せる．理由を書けない規則は，守る必要が無いか，別の規則の重複である．
    - 規則: 各規則には，それが守りたいことを添える．理由を書けない規則は削除の候補にする．
    - 見つけ方: 理由の無い規則を拾い，「なぜ」を 1 文で書けるかを問う．書けなければ削除候補として挙げる．

## 手順

1. 対象のファイルをすべて読む．
2. 原則ごとに，上の見つけ方で全ファイルを走査する．引用する箇所は grep で実在を確かめる．
3. 原則 3 と 5 は，ファイルをまたいで照合する（重複，別名，未定義）．
4. 所見を表にまとめる．列は 原則／場所（ファイルと引用）／欠陥（1 文．どの理由を損なうか）／修正案（短ければ置換後の文）．影響の大きい順に並べる．
5. 根本から見直すべき点（階層の逆転，無関係な話題の同居，判定できない起点）があれば，表の前に別立てで書く．
6. `--fix` があれば，表の順に修正を適用し，リポジトリの検査と formatter を通し，何を変えたかを述べる message で commit する．

## 完了条件

- 対象の全ファイルを読んだ．
- 11 の原則すべてについて走査した．該当なしの原則も，該当なしと書く．
- 引用した箇所はすべて実在する．
- 所見ごとに修正案がある．
- `--fix` のとき，リポジトリの検査と formatter が通り，作業ツリーが clean である．
